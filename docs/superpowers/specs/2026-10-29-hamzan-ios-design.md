## ねらいと成功の姿

Web 版「はむ算」は、学習エンジン（6 ステージ・61 レベル、ヒント→メモ→スピードの 3 モード、★判定、マスター、復習、診断）が完成しています。テストでも Python の参照実装と完全に一致しました。この資産をそのまま生かして iPhone で毎日使えるアプリにし、まずは Expo Go で実機確認できる状態を目指します。あわせて、練習を続けたくなる仕掛けとして「おへや」と「ショップ」を強化します。

成功の姿は次のとおりです。

* iPhone の Expo Go（PC と同じ Expo アカウントでサインイン）で QR コードを読むと起動し、Web 版と同じ学習の流れ（診断、毎日のセッション、復習）を最後まで使える
* おへやでハムスターが自分で動き回り、グッズで遊び、タップに反応する。見ているだけで楽しい
* 練習でためた「ひまわりのたね」でショップのグッズを買い、おへやに置ける
* リポジトリには Expo アプリに必要なファイルだけが残り、学習エンジンのテストは全件 PASS のまま
* 作業の途中経過が Git のコミットとして細かく残り、いつでも前の状態に戻せる

## 前提として決めたこと

ご要望にない部分は次のように決めました。違っていれば、開発を始める前に変更します。

1. Web 版は置き換えます。同じリポジトリを Expo アプリに作り替え、Web 版は最初のコミットとタグ `web-prototype` で Git の履歴に残します。
2. 対象は App Store 版の Expo Go を入れた iPhone（縦向き）です。App Store 版の Expo Go は、その時点の SDK のプロジェクトしか開けず、iPhone には古い版を入れられません。2026 年 9 月の公式ドキュメントでは SDK 54 で更新が止まっていたため SDK 54 で作りましたが、2026 年 11 月に App Store 版が SDK 58 に上がり、SDK 54 のプロジェクトを開けなくなったので SDK 58 へ上げました。これからも App Store 版の Expo Go と同じ SDK にそろえます。
3. ショップの通貨は「ひまわりのたね」です。練習でしか手に入らず、お金では買えません。ランダム要素（ガチャ）もありません。
4. 元の仕様にある「アプリ内通貨は使わない」（C-7）は、上の線を守る前提でショップに限って見直します。学習ルール（curriculum.json）は変えません。
5. パッケージ管理は README と同じ Bun を使い、テストも Bun で動かします。
6. Git はローカルに作成します。GitHub への push は、指示をもらってから行います。
7. 見た目はライトテーマのみとし、ダークモードは後回しにします。文字は iOS 標準の丸ゴシック（ヒラギノ丸ゴ）を基本にし、フォントのダウンロードを不要にします。
8. Expo Go 版は、開発中の確認と試しに遊ぶためのものです。PC で開発サーバーを動かしている間だけ遊べます。記録は Expo Go の中に保存され、将来の App Store 版には引き継がれません。
9. いちばん小さい画面は iPhone SE（第 2、第 3 世代、4.7 インチ、375×667pt）とし、出題画面はスクロールなしで収まるようにします。
10. 実機での確認は、iPhone をお持ちの方にお願いします（この PC は Windows で、iPhone のシミュレーターが使えないため）。開発側は、自動テストと、Expo の web 表示をブラウザで開く簡易確認で進めます。

## 目標と対象外

### 目標

* Web 版の学習機能をすべて iPhone で使える（61 レベル、3 モード、★判定、マスター、復習、毎日のセッション、診断、ステージチェック、チャレンジ、保護者画面）
* おへやのハムスターが自分で動き回り、グッズで遊び、タップに反応する
* 練習でためたたねで買えるショップ
* Web 専用と App Builder 専用のファイルを削除し、構成を整理する
* Web 版のレビューで見つかった不具合 3 件を直す

### 対象外

* App Store への公開（EAS Build、署名、審査、キッズカテゴリ対応）
* 課金とフリーミアム（curriculum.json の freemium 設定は Web 版と同じく使わない）
* Android の動作保証と iPad 専用レイアウト
* アカウント、クラウド同期、分析ツール、広告
* Web 版の記録の引き継ぎ（未公開のため不要）
* PC なしで毎日使うための配布（EAS Update、TestFlight、開発ビルド）と、記録の書き出しと読み込み

### やってはいけないこと

動いたとしても、次の状態になったら失敗とみなします。

* ショップが目的になり、簡単な問題を繰り返してたねを稼ぐのが一番得になる
* ガチャ、期間限定品、お金で買えるたね、広告など、子どもをあおる仕組みがある
* ハムスターがおなかをすかせる、元気がなくなるなど、休んだ子を責める仕組みがある
* 学習ルールや判定が変わり、golden テストが 1 件でも崩れる
* 速さだけでたねが増え、時間の圧力が強まる

## 制約

* Expo Go に入っているネイティブモジュールだけを使い、独自のネイティブコードや prebuild が必要な設定プラグインは使わない
* 使う予定のモジュールは expo-router、react-native-reanimated、react-native-gesture-handler、react-native-svg、react-native-safe-area-context、@react-native-async-storage/async-storage、expo-haptics、expo-audio、expo-keep-awake、expo-splash-screen
* どれも SDK 58 の expo パッケージの対応表（bundledNativeModules.json）に含まれる。主な版は React Native 0.88、React 19.3、Reanimated 4.7、Expo Router 58、react-native-svg 15.16、expo-audio 58、AsyncStorage 2.2
* SDK は App Store 版の Expo Go と同じ版（いまは 58）にそろえる。依存は `bunx expo install` で SDK 58 に合う版を入れる。Expo Go の SDK が上がったら、`bunx expo install expo@^<SDK>.0.0` と `bunx expo install --fix` でプロジェクトも上げる
* 実機の iPhone で開くには、PC の Expo CLI と iPhone の Expo Go を、同じ Expo アカウント（無料）でサインインしておく（`bunx expo login`）
* 学習ルールの数値は curriculum.json だけから読む（C-9）
* 記録は端末の中だけに保存する（C-1）
* 子ども向けの文言はひらがな中心にする（C-8）
* 元の仕様の制約のうち、リポジトリのコードから分かるのは C-1、C-7、C-8、C-9 だけ。C-2〜C-6 は未確認なので、仕様書があれば開発前に照らし合わせる
* この PC では `bun install` が接続数過多で失敗するため、`bun install --network-concurrency 4` を使う
* 実機確認は PC と iPhone を同じ Wi-Fi につなぐ。社内ネットワークでつながらない場合は `bunx expo start --tunnel` か、iPhone のテザリングを使う

## おへや：動き回るハムスター

### 部屋の構成

* 横長の部屋（設計上の座標は 400×260）を画面の幅に合わせて拡大縮小し、画面上部の 6 割ほどに表示する
* 背景は、かべ、まど、ゆか。その上にグッズとハムスターを重ねる
* グッズは決まった置き場所（スロット）に置く。スロットは 11 か所（ゆか・大 3、ゆか・小 3、かべ 2、てんじょう 2、まどべ 1）
* 既存の 8 つのグッズ（ごほうび）は、Web 版の位置に近いスロットへ自動で置く
* 手前にあるもの（y 座標が大きいもの）ほど上に描き、ハムスターがグッズの前と後ろを行き来できるようにする

### 行動のしくみ

`src/game/hamster-brain.ts` に、画面に依存しない純粋な TS で行動エンジンを作ります。

* 状態は「たいき」「さんぽ」「グッズであそぶ」「ねる」「タップへの反応」「おいわい」
* 次の行動は重み付きの抽選で決める。シード付きの乱数を使うので、テストで再現できる
* 持っているグッズが増えるほど、遊び方の種類が増える。同じグッズばかりが続かないようにする
* 夜（20 時から 6 時）は、おうちで寝ていることが多い。タップすると起きる
* たいき中は、まばたき、耳をぴくっと動かす、きょろきょろ、毛づくろい
* ときどき部屋を駆け回る「ダッシュ」をする
* おなかや元気などの数値は持たない。休んでも何も失わない

グッズごとの遊び方の例です。

* まわしぐるま：中に入って走り、車輪が速く回る。たまに転がり出て、びっくり顔になる
* ごはんざら：食べてほおぶくろがふくらみ、そのままおうちへ運ぶ
* きの おうち：中に入って「Zzz」。しばらくすると出てくる
* トンネル：片側から入り、反対側から出てくる
* べんきょうづくえ：小さな本を読み、「なるほど」の吹き出しを出す
* ひまわりの はち：においをかぐ
* ブランコとハンモック：ゆれる、ひるねする

### タッチへの反応

* ハムスターをタップすると、ぴょんと跳ねてハートと「きゅっ」の吹き出しを出し、軽く振動する
* 長押しすると、なでられて目を細める
* グッズをタップすると、ハムスターがそこへ行って遊ぶ
* ゆかをタップすると、そこまで歩いてくる
* ショップで買ったおやつをあげると、手前に来て食べる
* その日のゴールを達成していると、おへやに入ったときにお祝いの動きをする
* 新しいグッズを手に入れた直後は、そのグッズへ駆け寄って試す

### 描き方の方針

* 位置、向き、はずみは Reanimated の共有値で動かし、UI スレッドで描く。SVG 自体は描き直さず、包んだ View の transform だけを変える
* 歩くときの足の動きは、2〜3 枚のポーズの切り替えで表す。横向きの歩きポーズは新しく描く（正面の絵は Web 版を流用）
* 行動エンジンが JS 側で次の行動を決め、アニメーションの完了通知で次へ進む
* 端末の「視差効果を減らす」がオンなら、移動をゆっくりにし、跳ねる動きを減らす
* おへやが画面に出ていないとき（別のタブ、バックグラウンド）は止めて、電池を使わないようにする
* 経路探索はしない。スロットの配置を工夫し、直線の移動で済むようにする

## ショップとひまわりのたね

### 方針

元の仕様は「アプリ内通貨は使わない」（rewards.ts の C-7、curriculum.json の freemium.note）としています。今回はご要望に合わせてたねを導入し、次の線を守ります。

* お金では買えない
* ランダムな要素と期間限定品はない
* たねが減るのは買い物のときだけ。まちがいや休みでは減らない
* たねは学習の判定（★、モード、マスター、復習）に一切影響しない
* curriculum.json は変更せず、ショップに関するものは `src/game/` に置く

### たねのもらい方

たねの中心は「きょうの れんしゅう」（ウォームアップ、メイン、ステージチェック、復習）です。レベルを選んで自由に練習する「じゆう れんしゅう」は少なめにして上限を設け、簡単な問題の繰り返しが一番得にならないようにします。数値は初期値で、`src/game/economy.ts` の定数 1 か所で調整できるようにします。

| 内容                                | たね        |
|-----------------------------------|-----------|
| きょうの れんしゅうで、1 回目の答えが正解（ウォームアップ以外） | 1 問ごとに +1 |
| きょうの れんしゅうのセットを最後までやる             | +5        |
| ウォームアップをやる                        | +3        |
| じゆう れんしゅう（マスター前のレベル）で、1 回目の答えが正解  | 2 問ごとに +1 |
| じゆう れんしゅう（マスター前のレベル）のセットを最後までやる   | +2        |
| じゆう れんしゅう（マスターしたレベル）              | 0         |
| 診断とチャレンジで、1 回目の答えが正解              | 1 問ごとに +1 |
| きょうのゴールを達成                        | +20       |
| あたらしく ★2                          | +10       |
| マスター                              | +30       |
| ステージチェックに合格                       | +50       |
| 復習に合格（レベルごと）                      | +5        |
| じこベストを更新（1 レベルにつき 1 日 1 回まで）      | +5        |
| チャレンジでじこベスト                       | +10       |

* じゆう れんしゅうでもらえるのは、1 日 50 まで
* きょうの れんしゅう、診断、チャレンジは回数がもともと限られているので上限なし。節目のボーナスも上限なし
* 上限に達したら「きょうの たねは ここまで。れんしゅうは できるよ」と表示し、練習はそのまま続けられる
* マスターしたレベルの練習もできるが、たねは出ない（復習はきょうの れんしゅうに入るので、たねが出る）
* 中断したセット（判定しないセット）は 0。ただし、そのセットでその日のゴールに届いたときは、ゴールの +20 を出す
* 残りの区切りに出す問題がないときは、問題のあった最後のセットでゴールに届く
* 速さだけで増える分はない。速さに関係するのは、学習側にもともとある ★2 とじこベストの節目だけ
* 1 日の目安は、きょうの れんしゅうで 90〜100、じゆう れんしゅうを足しても 150 くらい。これで、きょうの れんしゅうが常に一番の稼ぎどころになる
* 判定は記録の種類で分ける。きょうの れんしゅうはセッションの一部として始めたセット、じゆう れんしゅうは「extra」のセット
* 結果画面に、たねの内訳（せいかい +24、さいごまで +5、★2 +10 など）を出す

## 不具合の扱い

Web 版のレビューで見つかった不具合は、移植と同時に直します。

* 一時停止中にバックグラウンドへ移ると解答時間が 0 になる件は、「時間を数えない区間」を一時停止とバックグラウンドの和集合で管理する時計（`src/platform/active-clock.ts`、純粋関数）で直す。AppState の active、inactive、background で検知し、再現したケースをテストに固定する
* 一時停止で入力途中の状態が消える件は、一時停止中も回答部品を消さずに「いちじ ていし」の幕をかぶせて直す（問題は見えなくする）。ヒントモードで答えが出たあとに一時停止して再開しても不正解扱いのままであることをテストする
* 保護者画面の入力テストが使用中の子に保存される件は、保存の処理にプロフィール ID を渡して直す
* Web 特有の指摘（lang、テンプレートの通信、バンドルサイズ、未使用の依存）は、Web 部分の削除で解消する
* テスト用のタブは、設定フラグ（app.json の extra）で出し分ける。Expo Go で確認する間は表示しておく
* Python 参照実装との突き合わせは、`tests/domain/common.ts` で python3、python の順に探し、`PYTHONUTF8=1` を付けて Windows でも動くようにする

## Git の運用

* 開発の最初に `git init` し、`.gitignore`（node_modules、.expo、dist、ios、android、ログ、.env.local など）を置く
* 最初のコミットは、いまの Web 版をそのまま入れたもの。タグ `web-prototype` を付ける
* main に小さなコミットを積み、フェーズの終わりにタグを付ける（v0.1、v0.2、v0.3、v1.0-expo-go）
* 1 コミットは 1 つの変更（削除、移植、機能追加、テスト追加を分ける）にし、どのコミットでも型チェックとドメインテストが通る状態を保つ
* メッセージは Conventional Commits（英語、命令形、100 バイト未満）。最後に絵文字と「- Generated by Copilot」、Co-authored-by を付ける
* GitHub への push は、指示があってから行う（プライベートリポジトリを作成）

## リスクと対策

* App Store 版の Expo Go は最新の SDK にしか対応しないので、Expo Go の SDK が上がると、それまでの SDK のプロジェクトは開けなくなる（2026 年 11 月に SDK 54 から 58 へ上げたのはこのため）。Expo Go の SDK が上がったら、プロジェクトの SDK も上げる。依存は必ず `bunx expo install` で入れる
* この PC の npm の取得先は、新しい版が npm に出てから 1 週間ほど遅れて届く。`bunx expo install --fix` が新しい版を見つけられないときは、`EXPO_OFFLINE=1` を付けて、入っている expo に同梱の対応表の版にそろえる
* Expo Go の中の記録は、将来の App Store 版へは移らない。毎日使うようになったら、記録の書き出しと読み込み（expo-sharing、expo-file-system）を追加する
* 社内ネットワークで実機につながらない場合は、`--tunnel` かテザリングを使う
* `bun install` の接続エラーには `--network-concurrency 4` で対応する
* 保存データの書き込みが遅くなったら、上限の維持と画面状態の非保存で抑え、それでも遅ければ expo-sqlite の kv-store に替える
* おへやの描画が重くなったら、動かすのを transform だけに絞り、同時に動くものを減らし、画面外では止める
* ショップが目的にならないよう、1 日の上限、少額の積み上げ、節目のボーナス重視、速さで増えないことを守る
* 移植で学習の結果が変わらないよう、ドメインは変更せず、recordSet のテストと golden テストで確かめる
